## 주제별 요약

### 게임 순위표 요구사항

- 상위 10명과 특정 사용자 순위 표시 요구사항
  - 동점자 처리 방식 논의 필요
  - 사용자 주변 순위 ±4까지 표시 기능 포함
- 실시간 점수 업데이트와 확장성, 안정성 요구
  - 최대 500만 사용자, 초당 250 요청 피크 가정
  - 검색 QPS는 평균 500, 최대 2500 예상
- API 설계
  - 점수 갱신 요청은 게임 서비스가 처리, 클라이언트 직접 요청은 부적절
  - 클라이언트는 순위표 조회만 직접 수행
- 메시지 큐 도입은 요구사항에 부합하지 않아 제외

### 리더보드 설계 및 데이터베이스 선택

- 관계형 DB는 실시간성 및 확장성 문제로 기각
- 레디스 채택 이유
  - 메모리 기반 keyvalue 스토어로 빠른 읽기/쓰기
  - 정렬 집합(zset) 자료구조 제공으로 순위 관리 용이
  - 내부적으로 해시 테이블과 스킵 리스트로 구현
- 스킵 리스트를 통한 효율적 탐색과 삽입
  - 대부분 연산이 O(log N) 시간 복잡도
- 데이터 규모 및 안정성 고려
  - 2500만 명 사용자 정보 저장 가능, 약 650MB 메모리 예상
  - 레디스 영속성 옵션과 복제(replica) 구성으로 안정성 확보
- 관계형 DB는 점수 기록 등 비실시간 데이터 저장용으로 활용
- 클라우드 환경과 자가 서비스 환경 모두 고려
  - AWS Lambda 등 서버리스 활용 가능성 언급
  - 트래픽 증가 시 자동 확장 기대

### 데이터 파티셔닝 및 확장 전략

- 고정 파티션과 해시 파티션 방식 비교
  - 고정 파티션은 점수 범위 기준으로 나누어 관리
  - 해시 파티션은 키 기반 자동 분산 제공하나 순서 유지 어려움
- 해시 파티션은 순위 계산과 특정 사용자 순위 조회에 비효율적
- 고정 파티션 채택 권고
- 캐시 도입으로 성능 개선 시도
- 레디스 노드 크기 조정 시 메모리 용량 2배 확보 권장
- NoSQL 대안으로 DynamoDB 검토
  - 전역 보조 인덱스(GSI) 활용해 다양한 쿼리 지원
  - 월별 데이터 파티셔닝 시 핫스팟 문제 발생 가능
  - 상위 10명 조회 및 특정 사용자 순위 산출 어려움 존재
  - 실시간성은 다소 제한적, 캐싱 및 배치 작업으로 보완 가능

### 게임 점수 및 난수 처리

- 점수 인플레이션 문제와 절삭 처리
  - 상위 8자리 정도만 표시, 하위 자릿수는 절삭
  - 동점자 처리 시 역산 방식 논의
- 게임 내 데미지 및 확률 요소의 랜덤성 한계
  - 실제 무작위와 인간 인지 무작위 차이 존재
  - 컴퓨터 난수 생성기의 시드 및 패턴 문제
  - 특정 시간대 난수 몰림 현상 발생
- 게임에서 확률 보정 기법 도입
  - 실패 시 확률 상승, 천장 시스템 적용
  - 사용자 체감과 게임 재미를 위한 보정 필수
- 난수 생성과 확률 보정은 게임 설계 핵심 요소
